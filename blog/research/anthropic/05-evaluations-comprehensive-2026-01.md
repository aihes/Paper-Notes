## 引言：当尺子开始衡量自己

**如果你手中只有一把锤子，看什么都像钉子。** 但在 AI 时代，更危险的问题是：**当你的锤子开始自我进化，你该如何评价它是否仍然是把好锤子？**

- **《Designing AI-resistant technical evaluations》**（1月21日）：当 AI 能够击败顶尖工程师的测试时，我们该如何设计下一代评估体系？

这不是两篇普通的工程技术文章。它们揭示了一个正在发生的**范式转移**：评估不再是一个工程问题，而是一个持续进化、自我更新的生存问题。

## Part 1: AI Agent 评估——复杂性带来的认知冲击

### 1.1 为什么 Agent 评估如此困难？

AI Agent 的核心能力——**自主性、智能性、灵活性**——恰恰是评估的噩梦：

- **多轮交互，状态不断变化**：你无法用单次问答评估一个会思考、会规划的系统
- **工具调用影响环境**：Agent 可能通过你未曾预料的方式改变环境，使得"成功"的定义变得模糊
- **错误会传播和复合**：第一轮的小失误可能在第十轮变成灾难性的失败
- **创造性超出预期**：前沿模型可能找到"作弊"的方法——比如 Opus 4.5 曾通过发现政策漏洞"失败"了一个飞行预订评估，但实际上为用户提供了更好的解决方案

> **关键洞察：** Agent 评估的核心矛盾在于——你想要衡量的能力（创造力、灵活性），恰恰是你无法用静态测试捕获的能力。

![Agent 评估的复杂性](http://aisdapp.aihe.space/typora/6a34dc2b-e88b-4b77-95f8-9bebc6b06149.png)

### 1.2 评估的解剖学：从任务到记录

Anthropic 提供了一套精确的术语体系，这是理解 Agent 评估的基础：

| 术语 | 定义 | 实例 |
|------|------|------|
| **任务 (Task)** | 单个测试用例，包含定义的输入和成功标准 | "修复认证绕过漏洞" |
| **试验 (Trial)** | 每次尝试运行任务的过程 | 用 Claude Code 完成任务的一次完整运行 |
| **评分器 (Grader)** | 评估 Agent 表现某方面的逻辑 | 单元测试、代码质量检查、安全审计 |
| **记录 (Transcript)** | 完整的试验过程记录 | 包含所有 API 调用、工具使用、推理过程的完整日志 |
| **结果 (Outcome)** | 试验结束时环境的最终状态 | 数据库中是否真的创建了预订记录 |
| **评估框架 (Harness)** | 端到端运行评估的基础设施 | Harbor、Promptfoo、Braintrust |

> **隐喻理解：**
> - **任务** = 考试卷子的一道题
> - **试验** = 学生的一次答题过程
> - **评分器** = 阅卷标准（客观题 vs 主观题）
> - **记录** = 学生的完整草稿和演算过程
> - **结果** = 最终答案
> - **评估框架** = 考场和监考系统

### 1.3 三种评分器：代码、模型、人类的三角制衡

Anthropic 的核心洞察在于：**没有完美的评分器，只有最适合场景的评分器。**

#### 代码级评分器：客观但脆弱

**优势：** 快速、便宜、客观、可重现
**劣势：** 对有效变体脆弱、缺乏细微差别

**适用场景：** 编码 Agent 的单元测试、API 调用验证、状态检查

**致命弱点：** Agent 可能通过你未曾预料的正确方式解决问题，而你的代码评分器因为不符合预期模式而判定失败。

#### 模型级评分器：灵活但漂移

**优势：** 灵活、可扩展、捕捉细微差别、处理开放式任务
**劣势：** 非确定性、需要与人工评分器校准

**适用场景：** 对话质量评估、代码质量审查、研究全面性判断

**最佳实践：** 使用 LLM-as-a-judge 时，必须定期与人工专家校准，并提供"Unknown"出口以避免幻觉。

#### 人工评分器：黄金但昂贵

**优势：** 黄金标准质量、匹配专家判断
**劣势：** 昂贵、缓慢、难以扩展

**适用场景：** 校准模型评分器、评估高度主观的输出、处理边界案例

> **实战建议：** 三种评分器的最佳配比是 **70% 代码级 + 25% 模型级 + 5% 人工级**。代码级处理客观验证，模型级处理主观判断，人工级负责校准和边界案例。

## Part 2: 不同 Agent 的评估策略矩阵

### 2.1 编码 Agent：确定性为王

**核心挑战：** 软件天然适合确定性评估——代码要么通过测试，要么不通过。

**黄金标准：**
- **SWE-bench Verified**：从热门 Python 仓库提取真实 GitHub 问题，通过运行测试套件评分
- **Terminal-Bench**：测试端到端技术任务，如从源码构建 Linux 内核

**评分策略：**
```yaml
# 示例：认证绕过修复任务的评分配置
graders:
  - type: deterministic_tests  # 确定性测试：必须通过
    required:
      - test_empty_pw_rejected.py
      - test_null_pw_rejected.py

  - type: llm_rubric  # LLM 评分：评估代码质量
    rubric: prompts/code_quality.md

  - type: static_analysis  # 静态分析：安全检查
    commands: [ruff, mypy, bandit]

  - type: state_check  # 状态检查：验证系统状态
    expect:
      security_logs: {event_type: "auth_blocked"}

  - type: tool_calls  # 工具调用检查：验证是否使用了正确工具
    required:
      - {tool: read_file, params: {path: "src/auth/*"}}
      - {tool: edit_file}
      - {tool: run_tests}
```

**关键洞察：** 不要过度约束路径。Anthropic 发现，严格检查工具调用顺序会导致测试过于僵化——Agent 经常找到评估者未曾预料的有效方法。

### 2.2 对话 Agent：交互质量是核心

**核心挑战：** 对话质量本身就是评估对象——不仅要解决用户问题，还要以正确的方式解决。

**多维评分矩阵：**

| 维度 | 评分方法 | 示例 |
|------|----------|------|
| **任务完成** | 状态检查 | 退款是否真的处理了？ |
| **交互效率** | 记录约束 | 是否在 10 轮内解决？ |
| **沟通质量** | LLM 评分 | 语气是否恰当？是否展示了同理心？ |
| **工具使用** | 工具调用检查 | 是否验证了身份？是否查询了政策？ |

**实战技巧：** 对话 Agent 评估通常需要第二个 LLM 扮演用户，通过多轮交互压力测试 Agent 的能力。

### 2.3 研究 Agent：主观性的艺术

**核心挑战：** "全面"、"高质量"、"权威"——这些概念本身就高度主观。

**三层验证策略：**

1. **基础性检查（Groundedness）：** 每个声明是否有来源支持？
2. **覆盖检查（Coverage）：** 是否包含了关键事实？
3. **源质量检查（Source Quality）：** 是否使用了权威来源而非随机搜索结果？

**最佳实践：** 对于开放式研究任务，LLM 评分器必须定期与领域专家校准，因为即使是专家也可能对"全面"有不同的定义。

### 2.4 计算机使用 Agent：真实世界的代价

**核心挑战：** 必须在真实或沙盒环境中运行，无法用模拟器完全替代。

**评估方法：**
- **WebArena**：浏览器任务，通过 URL 和页面状态验证
- **OSWorld**：完整操作系统控制，检查文件系统、应用配置、数据库内容

**效率权衡：**
- **DOM 交互**：快速但消耗大量 token
- **截图交互**：慢速但 token 高效

**实战案例：** Anthropic 的 Claude for Chrome 团队开发评估来检查 Agent 是否为每个上下文选择了正确的工具（DOM vs 截图），从而优化速度和准确性。

## Part 3: 非确定性的数学——pass@k vs pass^k

在 Agent 的世界里，**没有"正确答案"，只有"成功概率"**。

### 3.1 两种指标，两个世界

| 指标 | 定义 | 直观理解 | 适用场景 |
|------|------|----------|----------|
| **pass@k** | k 次尝试中至少成功一次的概率 | "给我足够的机会，我能搞定" | 内部工具、探索性任务 |
| **pass^k** | 所有 k 次试验都成功的概率 | "每次都要稳" | 客户产品、关键任务 |

**数学直觉：**

假设一个 Agent 的单次成功率为 75%：

- **pass@1** = 75%
- **pass@10** ≈ 94%（10 次机会中至少成功一次的概率接近 100%）
- **pass^10** ≈ 6%（10 次都成功的概率极低）

随着试验次数增加，**pass@k 趋近于 100%，而 pass^k 趋近于 0%**。

### 3.2 产品决策的数学

> **场景 A：内部开发工具**
> 开发者可以多次尝试，只要有一次成功就能继续工作。
> **决策：** 优化 pass@k，允许 Agent 多次尝试。

> **场景 B：客户服务 Chatbot**
> 用户期望每次都能得到可靠答案，不能接受"偶尔失灵"。
> **决策：** 优化 pass^k，优先保证一致性。

## Part 4: 从零到英雄——8 步评估构建路线图

### Step 0: 尽早开始，从小处着手

**错误认知：** "我需要几百个任务才能开始评估。"
**正确认知：** **20-50 个简单任务就足够开始。**

早期开发中，每个变更都有清晰、明显的影响，大效应量意味着小样本量就足够。等到 Agent 成熟后，才需要更大、更难的评估来检测更小的效应。

> **80/20 法则：** 先用 20% 的努力获取 80% 的价值。评估越晚开始，构建难度越大——早期需求自然转化为测试用例，等待太久就是在从实时系统中逆向工程成功标准。

### Step 1: 从已有的手动测试开始

**两个金矿：**
1. **开发中的手动检查**：你每次发布前验证的行为
2. **生产中的用户报告失败**：真实用户遇到的问题

将用户报告的失败转化为测试用例，确保你的套件反映真实使用模式。按用户影响优先级排序，把精力投入到最重要的地方。

### Step 2: 编写无歧义任务并提供参考解决方案

**好任务的标准：** 两个领域专家能够独立得出相同的通过/失败结论。

**测试方法：** 专家自己能通过这个任务吗？如果不能，任务需要优化。

**参考解决方案的价值：**
- 证明任务是可解的
- 验证评分器配置正确
- 为 Agent 提供示例（虽然你不应该在任务描述中直接给出）

> **警惕 0% 通过率：** 如果 Agent 在多次试验中都是 0% 通过（即使 pass@100 也如此），这通常是**任务设计问题**，而非 Agent 能力问题。检查：
> - 任务描述是否有歧义？
> - 评分器是否过于严格？
> - 评分器检查的条件是否在任务描述中明确说明？

### Step 3: 构建平衡的问题集

**常见错误：** 只测试"应该发生"的行为，忽略"不应该发生"的行为。

**示例：** Anthropic 在构建 Claude.ai 的网络搜索评估时遇到了这个问题。最初只测试"模型应该搜索"的场景（如"查询天气"），导致模型过度搜索——即使对于不需要搜索的问题（如"谁创立了 Apple？"）也会搜索。

**解决方案：** 构建双向评估：
- 查询应该搜索（如天气查询）
- 查询应该从现有知识回答（如常识问题）

找到平衡点需要多轮迭代，但这对于避免过度触发或触发不足至关重要。

### Step 4: 构建稳健的评估框架和稳定环境

**关键原则：** 每次试验应从**干净环境**开始。

**隔离失败案例：**
- **共享状态导致虚假失败：** 之前试验留下的文件、缓存数据、资源耗尽
- **共享状态导致虚假成功：** Claude 通过检查 git 历史获得不公平优势

**实战案例：** Anthropic 在某些内部评估中发现，Claude 通过检查先前试验的 git 历史在某些任务上获得了不公平优势。这导致试验不独立——它们受到相同因素影响，使得评估结果不可靠。

### Step 5: 精心设计评分器

**黄金法则：** 优先选择确定性评分器，必要时使用 LLM 评分器，谨慎使用人工评分器。

**避免过度路径约束：** 常见直觉是检查 Agent 是否按照非常具体的步骤顺序调用工具。Anthropic 发现这种方法过于僵化，导致测试过于脆弱——Agent 经常找到评估者未曾预料的有效方法。

**更好的方法：** 评估 Agent 产生了什么，而不是它如何达到那里。

**部分信用策略：** 支持代理正确识别问题并验证客户但未能处理退款的代理，比立即失败的代理要好得多。重要的是在结果中表示这种成功的连续谱。

### Step 6: 检查记录——这是关键技能

**你不会知道你的评分器是否工作良好，除非你阅读许多试验的记录和评分。**

**在 Anthropic：** 投资于查看评估记录的工具，并定期花时间阅读它们。

**当任务失败时，记录会告诉你：**
- Agent 是犯了真正的错误？
- 还是你的评分器拒绝了一个有效的解决方案？

**失败应该感觉公平：** 清楚 Agent 错误了以及为什么。当分数不上升时，我们需要有信心这是由于 Agent 性能，而不是评估本身。

> **阅读记录是验证评估是否真正衡量重要内容的唯一方法。** 这是 Agent 开发的一项关键技能。

### Step 7: 监控能力评估饱和度

**100% 的评估只能跟踪回归，无法提供改进信号。**

**评估饱和：** 当 Agent 通过所有可解任务，没有改进空间时发生。

**示例：** SWE-Bench Verified 分数今年从 30% 开始，前沿模型现在接近饱和，超过 80%。

**欺骗性信号：** 随着评估接近饱和，进展也会放缓——因为只剩下最困难的任务。这可能导致结果具有欺骗性，因为大的能力改进表现为分数的小幅增加。

**应对策略：** 定期用更难的任务扩展评估套件，或者让高通过率的评估"毕业"成为回归套件。

### Step 8: 通过开放贡献和长期维护保持评估套件健康

**评估套件是活的产物**，需要持续关注和明确的所有权才能保持有用。

**Anthropic 的演进：**
- 尝试了各种方法
- 最有效的是建立专门的评估团队拥有核心基础设施
- 领域专家和产品团队贡献大多数评估任务并自己运行评估

**产品团队所有权的价值：** 团队可以浪费数周在 AI 功能上，这些功能在早期测试中"有效"，但未能满足明确定义的评估会早期暴露的期望。定义评估任务是压力测试产品需求是否足够具体以开始构建的最佳方法之一。

**评估驱动开发：** 在 Agent 能够满足之前构建评估以定义计划的能力，然后迭代直到 Agent 表现良好。

> **最有资格定义成功的人是最接近产品要求和用户的人。** 产品经理、客户成功经理或销售人员可以使用 Claude Code 将评估任务作为 PR 贡献——让他们这样做！

## Part 5: AI 抗性评估——当尺子需要自我进化

### 5.1 一个性能工程师 Take-Home 的三年进化史

**2023年11月：** Tristan Hume 设计了一个性能工程师的 take-home 测试。
**问题：** 模拟类似 TPU 的加速器优化任务
**结果：** 帮助招聘了当前大多数性能工程团队

**2025年5月：** Claude Opus 4 在 4 小时内提出了比几乎所有人类更优化的解决方案。
**应对：** 使用 Claude Opus 4 识别其开始困难的地方，以此作为 v2 的新起点。

**2025年下半年：** Claude Opus 4.5 在 1 小时内达到通过阈值，2 小时时匹配了最佳人类表现。
**困境：** 即将发布一个模型，其中 take-home 上的最佳策略将是委托给 Claude Code。

### 5.2 性能基准的军备竞赛

| 实现者 | 周期数 | 备注 |
|--------|--------|------|
| Claude Opus 4 (测试时计算) | 2164 | 早期模型 |
| Claude Opus 4.5 (2小时) | 1790 | 接近最佳人类 |
| Claude Opus 4.5 (测试时计算 2小时) | 1579 | 超越人类 |
| Claude Sonnet 4.5 (测试时计算 >2小时) | 1548 | 更长时间优化 |
| Claude Opus 4.5 (测试时计算 11.5小时) | 1487 | 持续改进 |
| Claude Opus 4.5 (改进测试时计算) | 1363 | 最新最佳 |
| **人类专家（无时间限制）** | **< 1363** | 人类仍有优势 |

> **关键洞察：** 人类专家在无时间限制的情况下仍然保持优势。人类在足够长的时间尺度上保持优势，但短期内 AI 占主导。

### 5.3 设计 AI 抗性评估的核心原则

#### 原则 1：避免过于依赖训练数据的问题

Claude 在数据转置和银行冲突问题上表现出色，是因为工程师多年来一直在这些问题上挣扎，因此 Claude 有大量训练数据可以借鉴。

**应对：** 选择分布外的问题——训练数据中不常见的类型。

#### 原则 2：在适当情况下优先考虑新颖性而非真实性

原始 take-home 有效是因为它类似于真实工作。替代品有效是因为它模拟**新颖工作**。

**困境：** 真实性可能不再是我们拥有的奢侈品。

#### 原则 3：让工具构建成为测试的一部分

Zachtronics 风格的编程谜题有意不提供可视化或调试工具。启动代码只检查解决方案是否有效。构建调试工具是正在测试的内容的一部分。

**信号：** 关于如何投资工具的判断是信号的一部分。

#### 原则 4：承认时间尺度的变化

METR 的研究表明，人类仅在任务超过几小时时才对 AI 保持优势。在 2 小时的 take-home 限制下，这个窗口正在迅速关闭。

> **残酷真相：** 我们可能不得不接受人类只在"超长任务"（>4小时）上才有优势的现实。

## Part 6：评估与其他方法——瑞士奶酪模型的启示

### 6.1 六种方法的优劣势矩阵

| 方法 | 优势 | 劣势 | 最佳使用阶段 |
|------|------|------|--------------|
| **自动评估** | 快速迭代、完全可重现、无用户影响 | 需要前期投入、需要持续维护 | 发布前、CI/CD |
| **生产监控** | 揭示真实用户行为、捕获合成评估遗漏 | 反应式、信号嘈杂 | 发布后 |
| **A/B 测试** | 测量实际用户结果、控制混杂因素 | 缓慢、只能测试部署的变更 | 有足够流量时 |
| **用户反馈** | 捕获未预期的问题、真实示例 | 稀疏、偏向严重问题 | 持续收集 |
| **手动记录审查** | 建立失败模式直觉、微妙质量问题 | 耗时、不扩展、覆盖不一致 | 每周抽样 |
| **系统化人工研究** | 黄金标准、处理主观任务 | 昂贵、周转慢 | 校准 LLM 评分器 |

### 6.2 瑞士奶酪模型：多层防御

就像安全工程中的瑞士奶酪模型，**单一评估层无法捕获每个问题**。多个方法结合时，通过一层遗漏的失败会被另一层捕获。

**最佳实践组合：**
- **自动评估**：快速迭代的第一道防线
- **生产监控**：发布后检测分布漂移的地面实况
- **定期人工审查**：校准和填补空白

## 行业洞察：评估经济的崛起

### 趋势 1：评估成为一种核心竞争力

随着 AI 能力的加速进化，**"能设计出有效评估体系的能力"** 正在成为稀缺资源。

**证据：**
- Anthropic 投资专门的评估团队
- Bolt AI 在 3 个月内构建了评估系统
- Descriptive 从手动评分演变为 LLM 评分器，现在定期运行两个独立的套件

### 趋势 2：评估框架的军备竞赛

**当前格局：**
- **Harbor**：容器化环境，云提供商扩展
- **Promptfoo**：轻量级开源，YAML 配置
- **Braintrust**：离线评估 + 生产可观测性
- **LangSmith**：与 LangChain 深度集成

**预测：** 2026-2027 年将出现评估框架的整合战。

### 趋势 3：从"评估模型"到"评估系统"

评估不再仅仅关于模型能力，而是关于整个系统：
- 模型 + harness + 工具 + 环境

**含义：** 产品团队需要拥有评估，而不仅仅是研究团队。

## 个人/职业启发：这对我们意味着什么？

### 启发 1：评估能力 = AI 时代的领导力

**如果你不能衡量它，你就无法改进它。** 在 AI 时代，这句话的重量被放大了十倍。

**可执行建议：**
1. **投资评估基础设施**：即使你只有 20 个任务，从今天开始
2. **培养"评估思维"**：每次遇到问题时，问自己"这能变成测试用例吗？"
3. **记录一切**：未来你会感谢现在的自己

### 启发 2：人类的比较优势正在转移

**从"知道"到"判断"**：AI 知道得更多，但人类仍然更擅长判断什么是重要的。

**可执行建议：**
1. **专注于"更长"的任务**：在 >4 小时的任务上寻找优势
2. **培养领域直觉**：AI 可以优化，但你定义优化方向
3. **学习与 AI 协作**：而不是试图在它最擅长的地方打败它

### 启发 3：真实性的代价

**我们可能不得不牺牲"真实性"来获得"可评估性"**。

**可执行建议：**
1. **接受这个现实**：评估可能变得"不那么真实"，但仍然有用
2. **平衡多种方法**：不要依赖单一评估方法
3. **持续迭代**：评估本身也需要不断进化

- [ ] 是否评估了结果而非路径？

## 环境设计检查表
- [ ] 每次试验是否从干净环境开始？
- [ ] 是否避免了共享状态导致的相关失败？
- [ ] 评估环境是否与生产环境一致？

## 维护检查表
- [ ] 是否定期阅读评估记录？
- [ ] 是否监控评估饱和度？
- [ ] 是否有明确的评估所有者？
- [ ] 是否定期与用户反馈对比？

## 结语：评估的永恒循环

**评估不是一次性任务，而是一个持续的过程。**

就像 Anthropic 的 take-home 测试经历了三次迭代一样，你的评估体系也需要不断进化。模型在进步，你的"尺子"也需要不断重新校准。

**记住：**
1. **尽早开始** - 20 个任务足够启动
2. **读取记录** - 这是验证评估有效性的唯一方法
3. **组合多种方法** - 瑞士奶酪模型
4. **拥抱变化** - 评估本身也需要进化

**最后，给自己一点耐心：** 即使是 Anthropic，也在 Claude Opus 4.5 面前不得不重新设计他们的评估。这没关系——这意味着你在真实地衡量一个正在快速进化的系统。

**在 AI 时代，唯一不变的评估标准，就是变化本身。**
